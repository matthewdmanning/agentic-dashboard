# Review: #90-#96, since `9c71247`

Reviewed the nine commits from `9c71247` to `2966698` on `feat-shadcn-ui` for
defects, completeness against the issue each commit closes, and deliberate
shortcuts left unmarked. `npm run check` passes before and after the fixes
below (243 tests before, 253 after).

## Fixed

### 1. A killed key rotation destroyed every credential it had already re-encrypted

`rotateSecretKeyIfDue` persisted the new key ring only after
`rotateConnectionKeys` and `rotateQueryKeys` had finished rewriting both
stores. Those stores are written the moment a record is resealed, so any
interruption between the first store write and the final ring write — a
crash, a `SIGKILL`, power loss — left records on disk naming a `keyId` that
had only ever existed in memory. Nothing could open them again; the plaintext
is unrecoverable. Rotation runs at server startup, so the window is a normal
startup, not an exotic path.

This defeats #91's acceptance criterion "a failed re-encryption leaves the
original encrypted record usable": it holds for a record whose own
re-encryption throws, which is what the existing test covers, but not for a
pass that dies partway through.

Fixed by writing the ring once with the new key made current _before_ either
store is touched, keeping the existing write at the end to prune retired
keys. The failure mode inverts to a recoverable one: an interrupted pass now
leaves a persisted key that nothing references yet, which the next startup's
pass prunes on its own.

- `src/server/key-rotation.ts`
- Regression test in `src/server/key-rotation.test.ts` — a query store that
  cannot be read makes the pass throw partway through; the persisted ring
  must still carry the new current key and still open the connection.
  Verified failing against the pre-fix code.

### 2. A user identity was interpolated straight into a filesystem path

`writeUserComponentsConfig` built its output path as
`join(componentsDir, ${user}.json)`. An identity is an account name from the
auth store, not a validated path component, so a `/`, a `\`, or a `..` in one
decided where the file landed, and two identities differing only in
path-significant characters could collide on one file.

`src/auth/index.ts` already exports `encodeUserPathSegment` — "encodes an
identity as exactly one filesystem-safe, collision-free segment" — tested,
and until now called by nothing outside its own test. Reused it rather than
adding a check.

- `src/server/appearance.ts`
- Test in `src/server/appearance.test.ts` asserts an identity of
  `../../escaped` still writes exactly one file inside the directory, plus
  the two existing filename assertions updated
  (`src/service/index.test.ts`).

### 4. A base colour recoloured light mode partially and dark mode not at all

`baseColourTokenValues` was a hand-written table defining 11 of the 31 tokens
`presetTokens` names, light only. The other 20 (`popover`,
`card-foreground`, `destructive`, `input`, the `chart-*` and `sidebar-*`
families) kept `styles.css`'s neutral values whatever base colour was
selected, and there was no `.dark` block at all — `presetCss` emitted `:root`
_and_ `.dark`, `baseColourCss` emitted `:root` alone. So a preset covered both
modes and a base colour covered neither properly. Worse, a light-only `:root`
override would have _fought_ `styles.css`'s `.dark` block once anything
activated the class: equal specificity, and the injected block comes later in
source order, so light values would have won inside dark mode.

The values were also approximations — `slate` was written as
`oklch(0.208 0.042 265)` where shadcn's real value is
`oklch(0.208 0.042 265.755)`.

Rather than hand-write 310 more values, derived them from data already in the
repo. shadcn's base-colour token sets are a fixed mapping from semantic token
to Tailwind palette step, and the installed `tailwindcss` package ships that
palette in `theme.css`. Confirmed the mapping on both an achromatic and a
chromatic scale before relying on it — `neutral-950` is
`oklch(14.5% 0 none)`, shadcn's `--foreground` is `oklch(0.145 0 0)`;
`slate-950` is `oklch(12.9% 0.042 264.695)`, shadcn's slate `--foreground` is
the same.

So `basePalette` is now the five scales at the eleven steps the token sets
draw from, generated from `node_modules/tailwindcss/theme.css` and normalised
to the `oklch(L C H)` form `styles.css` uses; `lightTokens`/`darkTokens` are
the token-to-step mapping. Every base colour now yields all 31 tokens in both
modes.

Two project-specific details the mapping preserves rather than "corrects":
this project uses monochrome charts drawn from the selected scale (steps 300,
500, 600, 700, 800) rather than shadcn's stock multicolour set, and keeps
shadcn's stock blue for dark `sidebar-primary`. `destructive` stays red in
both modes — a base colour changes neutrals, not the meaning of a destructive
action.

Since both paths now produce a complete light/dark pair, `baseColourCss` and
`presetCss` collapsed into one `tokenSetCss`. `radius` stays a preset's to
set; the base-colour path leaves the project default alone.

- `src/server/appearance.ts`
- `src/server/appearance.test.ts` — three tests. The load-bearing one asserts
  that generating `neutral` reproduces `styles.css`'s own `:root` and `.dark`
  blocks, token for token: that is what pins the palette and the mapping to
  something real, and what will catch the generator and the stylesheet
  drifting apart. Verified non-vacuous by mutating a palette value.

### 5. A user's heading font reached nothing on screen

Found while settling #96's token question below, by checking how shadcn and
Tailwind actually resolve tokens and then reading this project's own compiled
CSS.

`typesetCss` applied fonts as selector rules — `main { font-family: … }` and
`main :is(h1, h2, h3, h4, h5, h6) { font-family: … }`. Both only ever reach
text that _inherits_ its font. A Tailwind font utility compiles to a
`font-family` declaration on the element itself, which beats inheritance
outright, so any component carrying one ignored the viewing user's typeset.

`CardTitle` carries `font-heading` and renders a `<div>`, not an `h1`-`h6` —
so the heading rule did not match it even on specificity, it did not match at
all. Card titles are the only headings this build renders, which made
`headingFont` entirely dead. Verified against `dist/`: the utility compiled to
`font-family: var(--font-sans)`, i.e. Geist, whatever the user chose.

The mechanism the docs describe is to override the custom property, not the
selector — the same indirection the colour tokens already use, and why
`--background` works while a font did not. `styles.css` blocked that for
fonts: `@theme inline` substitutes a declared value straight into the utility,
so `--font-sans: 'Geist Variable', sans-serif` baked a literal that nothing in
the cascade could reach.

Fixed by indirecting the font tokens through plain custom properties
(`--body-font`, `--heading-font`, `--monospace-font`) and having `typesetCss`
redefine those instead of writing `font-family` rules. Every component
carrying a font utility now follows the viewing user without naming a font of
its own. Project defaults are unchanged — `.font-heading` compiles to
`var(--heading-font)`, which still resolves to Geist until a user picks
otherwise.

- `src/styles.css` — font tokens in `@theme inline` now point at custom
  properties; the three defaults added to `:root`.
- `src/server/appearance.ts` — `typesetCss` emits the three properties; size,
  leading, and flow stay a `main` rule, as they are not tokens.
- `src/server/appearance.test.ts` — the typeset assertions now check the
  properties, and that the dead heading selector is gone.

### 6. Both integration notices went stale until a page reload

`App.tsx` loaded the blocked and unavailable-query notices once on mount and
never again. Blocking, unblocking, and removing an entry are all mutations, so

### 8. Settings could not add or update a personal preset

#96 requires users can "add, update, remove, and select only their own presets
without a permission check", and CONTEXT.md lists personal presets among what
Settings manages. Only select, remove, and clear existed; adding was reachable
only through MCP.

A preset is a whole token set, so it is pasted under a name rather than
assembled from sixty-odd colour inputs, and `parsePersonalPreset` validates it
against the same `namedPresetSchema` the service and the MCP tool accept -- a
partial set is refused in the panel, naming what is missing, rather than
travelling to the store to be rejected there. Reusing a name replaces that
preset, matching `add-personal-preset`'s upsert.

The upsert is deliberately not shared with `mcp/server.ts`: that would have
the MCP module importing a client module built around `fetch`, the wrong
direction for one line.

- `src/client/Settings.tsx`, `src/client/appearance-client.ts`,
  `src/client/Settings.test.tsx`

## Reported, not fixed

Both remaining items are security-shaped, and are deliberately left for a pass
of their own rather than folded into this one.

1. **`blockedIntegrationNotices` decrypts a credential to answer a question
   that is not about the credential.** It calls `connections.get(user, id)`
   per blocked entry purely to test whether a connection exists, and `get`
   runs AES-GCM open. The stored envelope already carries `owner` and
   `catalogEntryId` in cleartext, so the answer needs no key at all. Not a
   live failure -- just unnecessary crypto on secret material, which sits
   awkwardly against ARCHITECTURE.md's "`CredentialStore` is the single seam
   every path goes through to reach a stored secret". The fix is an
   envelope-only `ConnectionStore.listEntryIdsForOwner`, which costs updates
   to three in-memory test fakes. `src/service/index.ts`.

2. **`personalPresets` and `themeMapping` are unbounded.** Both are ungated by
   design (D35). `personalPresets` is an unbounded array, and each preset's
   `themeMapping` is `z.record(z.string().min(1), ...)` -- arbitrarily many
   keys of arbitrary length. Any authenticated user can grow the shared
   appearance file without limit, which is a storage-exhaustion vector rather
   than a correctness bug. Single-host pre-alpha, so low priority, but it is
   the one user-writable unbounded structure in the contract, and Settings now
   has a control that writes to it.

## #96's token-generation requirement

The open question was whether `readCallerAppearance` building a stylesheet on
every read violates #96's "generate token values only when initialization or
preset application requires it; do not compute tokens during ordinary
requests". Checked against the shadcn and Tailwind documentation, and against
this project's compiled CSS.

shadcn's theming is two layers, and only one of them is generated:

- `@theme inline { --color-background: var(--background); … }` is the mapping.
  Tailwind compiles it at build time into utility classes. Tailwind's own docs
  are explicit that this is what `@theme` is _for_: "the `@theme` directive is
  used instead of `:root` because it instructs Tailwind to generate utility
  classes, whereas `:root` variables do not."
- `:root { --background: oklch(…) } .dark { … }` are plain CSS custom
  properties. Tailwind generates nothing from them. The shadcn CLI simply
  _writes_ these literals into `globals.css` once, at init, picked by
  `tailwind.baseColor`.

Because the mapping uses `inline`, a utility compiles to
`background-color: var(--background)` — confirmed in `dist/`. The value is
resolved by the browser through the cascade, per element, at paint time. That
is the whole per-user mechanism: redefining `--background` later in the
cascade recolours everything downstream, with no build step involved.

So "generating token values" means deriving an oklch palette from a base
colour name — the CLI's job, build-time only, which is exactly what D26
already says must not be re-run per user. `appearanceCss` never does this. It
reads a static table of literals and serialises them, which is the serving
step, not the generation step. The requirement is met.

Two consequences worth keeping:

- The requirement is about the shadcn CLI, not about string concatenation.
  Caching `appearanceCss` output would optimise nothing that #96 was
  protecting against.
- The idiomatic way to scope tokens is a scoping selector, which is precisely
  what `.dark` is. The base-colour path originally overrode `:root` alone,
  which fought the cascade rather than using it; item 4 above closes that by
  emitting a light and a dark block from both paths, the shape shadcn's own
  stylesheet demonstrates.
